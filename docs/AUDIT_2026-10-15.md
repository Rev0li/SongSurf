# Audit SongSurf — 2026-10-15

Audit en vue des prochaines versions. Périmètre : `SongSurf/` (server, watcher, frontend, Docker) + `chrome-extension/`.
État de départ : `main` @ `5d07632`, 201 tests serveur au vert (les 3 fichiers `test_watcher_*` ne se lancent pas en local : `PyJWT`/`docker` absents de l'environnement).

## Synthèse

Le produit est fonctionnel et la base est saine (containment `is_relative_to`, compare constant-time, JWT `HS256` + `exp` requis, utilisateur non-root, file de jobs serveur). Les priorités pour la suite :

1. **Sécurité** : la politique CORS du watcher est trop permissive (origine `null` + n'importe quelle extension) et un membre peut écraser les cookies YouTube globaux.
2. **Fiabilité** : arrêt du conteneur toujours en SIGKILL, file d'attente uniquement en mémoire, healthcheck cassé, yt-dlp mis à jour sans version figée à chaque boot.
3. **Équité multi-utilisateur** : quota journalier et file FIFO globaux ; `/api/status` expose le dernier titre/erreur des autres membres.
4. **Maintenabilité** : deux fichiers monolithiques (~2 000 lignes chacun), stack frontend vieillissante (Node 20 en fin de vie, Svelte 4), pas de CI.

## P0 — Sécurité

### S1. CORS : l'origine `null` et toutes les extensions sont acceptées avec credentials
`watcher/watcher.py:61` ajoute `'null'` aux origines autorisées, et `:484` accepte toute origine `chrome-extension://*`, avec `Access-Control-Allow-Credentials: true`. Le cookie `access_token` est en `SameSite=None` (`:552`).
- N'importe quel site peut obtenir l'origine `null` via une iframe `sandbox` → requêtes authentifiées **et lecture des réponses** (`/api/me`, `/api/library`, mise en file, déplacement/suppression de fichiers…). Le preflight passe aussi, puisque `null` est autorisé.
- Toute autre extension installée dans le navigateur a le même accès.
- **Fix** : supprimer `'null'` ; n'autoriser que l'ID de l'extension SongSurf (`CORS_EXTENSION_IDS=…` dans `.env`, ID stable via la clé `key` du manifest). À tester ensuite avec l'extension réelle (la remarque « some browsers send null for extensions » est à vérifier : en MV3, le service worker envoie `chrome-extension://<id>`).

### S2. `/api/cookies/update` ouvert à tous les membres
`server/app.py:1305` : n'importe quel utilisateur authentifié remplace le fichier global `/data/cookies.txt` qui sert à **tous** les téléchargements. Un membre peut donc casser les téléchargements des autres, ou y mettre son propre compte YouTube.
- **Fix** : réserver aux admins (ou passer à des cookies par utilisateur, `cookies-<pseudo>.txt`), plafonner la taille, valider le format Netscape.

### S3. Pas de limite de taille sur les requêtes
Pas de `MAX_CONTENT_LENGTH` sur Flask (uploads de pochettes, cookies, JSON). **Fix** : `app.config['MAX_CONTENT_LENGTH'] = 10 * 1024 * 1024`.

### S4. Fuite d'informations entre membres dans `/api/status`
`last_completed` (avec `file_path` et métadonnées) et `last_error` sont globaux et renvoyés à tout le monde ; seuls `pending` et `is_mine` sont filtrés. **Fix** : stocker les deux par `user_sub` et ne renvoyer que ceux de l'appelant.

## P1 — Fiabilité / exploitation

### R1. SIGKILL systématique à l'arrêt
`entrypoint.sh` fait `exec "$@"` → `app.py` devient PID 1. Sous Linux, PID 1 ignore SIGTERM tant qu'aucun handler n'est enregistré, et `app.py` n'en enregistre aucun. `watcher._stop_songsurf()` (`container.stop(timeout=15)`) attend donc 15 s puis Docker force en SIGKILL. Vérifié sur le NAS le 2026-10-14 : `docker stop -t 15 songsurf` → 16 s, exit 137, reproductible à 100 %.
Risque : un stop pendant une conversion ffmpeg laisse un fichier incomplet dans `/data/temp`.
**Fix** : `init: true` dans `docker-compose.yml` (le plus simple), puis un handler SIGTERM qui laisse finir le titre en cours ou nettoie `/data/temp`.

### R2. Healthcheck toujours « unhealthy »
`docker-compose.yml` utilise `${FLASK_PORT:-8081}`. Compose résout les `${...}` depuis le `.env` du host, pas depuis `environment:` du service : `FLASK_PORT` n'y existe pas, donc on retombe sur 8081, alors que le NAS tourne sur `SONGSURF_PORT=8000`. Observé le 2026-10-14 : `FailingStreak` à 443. Le `HEALTHCHECK` du `Dockerfile` (`SONGSURF_PORT`) est correct mais écrasé par le compose. Cosmétique : le watcher a son propre check.
**Fix** : `$$FLASK_PORT` (le `$$` échappe la variable pour qu'elle soit lue *dans* le conteneur) ou `${SONGSURF_PORT:-8081}`.

### R3. La file d'attente vit uniquement en mémoire
`job_queue`, `_pending_queue`, le compteur journalier et l'état des ZIP sont perdus à chaque redémarrage (crash, `make deploy-nas`, SIGKILL). Le watcher évite l'arrêt pendant un batch, mais pas les autres cas. **Fix** : journaliser les jobs dans un petit SQLite (`/data/state.db`) et les rejouer au démarrage. Ça simplifie aussi R5 et F1.

### R4. yt-dlp mis à jour à chaque boot, sans version figée
`entrypoint.sh` fait `pip install --upgrade yt-dlp` à chaque démarrage à la demande : ça rallonge le boot, ça dépend du réseau, et une release cassée de yt-dlp arrive en prod sans prévenir. **Fix** : épingler la version dans `requirements.txt`, la mettre à jour par une action volontaire (`make bump-ytdlp`), et garder la mise à jour au boot en option (`YTDLP_AUTO_UPDATE=false` par défaut).

### R5. `/api/prepare-zip` synchrone
Le ZIP de toute la bibliothèque est construit pendant la requête : risque de timeout du proxy sur une grosse bibliothèque, et il est compressé en `ZIP_DEFLATED` alors que du MP3 ne se compresse presque pas. **Fix** : `ZIP_STORED`, et génération en arrière-plan + polling (même modèle que genre-backfill).

### R6. Serveur de développement Flask en production
`app.run()` dans les deux services. Ça marche pour l'usage actuel, mais pas de gestion propre des timeouts ou du nombre de connexions. **Fix** : `waitress` (pur Python, multi-thread, compatible avec le worker singleton) — **pas** gunicorn multi-process, car l'état est global au process.

### R7. Divers
- `entrypoint.sh` crée encore `/data/plex_music` (reste de l'ancien code).
- `cancel_flag` : code mort (documenté). Soit on câble une route `/api/cancel` (voir F2), soit on le supprime.

## P2 — Équité multi-utilisateur

### E1. Quota journalier global
`_daily_count` est commun à tous : un membre peut épuiser le quota de tout le monde, admin compris. **Fix** : compteur par `user_sub` (admin exempté ou avec sa propre limite).

### E2. File FIFO globale
Un membre qui met 20 albums en file bloque les autres pendant des heures. **Fix** : round-robin entre utilisateurs dans le worker (une file par `user_sub`, on prend tour à tour un job dans chacune).

## Pistes fonctionnelles pour les prochaines versions

- **F1. Historique des téléchargements par utilisateur** (dépend de R3/SQLite) : liste, statut, « relancer les échecs ».
- **F2. Annulation** : annuler un job en attente ou le titre en cours (câbler `cancel_flag`, retirer de la file).
- **F3. Notifications de fin de batch** (toast + événement rev0auth `batch_done`), utile maintenant que la file tourne sans onglet ouvert.
- **F4. Intégration Jellyfin** : déclencher un scan de bibliothèque via l'API Jellyfin après un batch admin.
- **F5. Audit metadata à l'échelle de la bibliothèque** (aujourd'hui par artiste) avec rapport global.
- **F6. Sauvegarde de la bibliothèque admin** (rsync/snapshot), puisque l'export ZIP des membres purge par conception.
